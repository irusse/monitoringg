# Тест: ПЦН «Тревога» и СКУД RDM6300

Две платы Heltec V4, один образ `heltec_v4_access`. Нода у панели читает сухой контакт. Нода мониторинга показывает тревогу и пускает по RDM6300. Журнал — экран **События** во Flutter (`app/mesh485`) и `EVENT_LIST`. Штатное приложение MeshCore остаётся для ключей и repeater; строка «Тревога» в его чате не является проверкой.

Распиновка: [`pinout.md`](pinout.md). Провода: [`../hardware/wiring.md`](../hardware/wiring.md).

Сборка тестов без платы:

```
cd firmware/heltec_v4
py -3.13 -m platformio run -e native_protocol_tests
.pio\build\native_protocol_tests\program.exe
```

Ожидание: `native_protocol_tests: ok`.

Flutter:

```
cd app/mesh485
C:\flutter\bin\flutter.bat test
```

Прошивка платы: `pio run -e heltec_v4_access -t upload`. Второй узел собирать с `-D MESH485_NODE_ID=\"EXT-002\"`. Антенна надета до любого TX.

## Когда можно начинать

| Момент | Что уже можно | Чего ещё нет |
|---|---|---|
| Сейчас, до прогона 25 | Собрать оптопару и делитель на столе. Мультиметром убедиться, что на GPIO не приходит 5 В и не приходит 12 В. Companion по USB/BLE как раньше | Контакт не станет событием. Вторая нода тревогу не увидит. RDM6300 карты не прочитает |
| После прогона **25** | Замыкание GPIO 47 на ноде у панели → одно `ALARM` в `EVENT_LIST` и на OLED. Flutter «События» по USB этой ноды | Передача на вторую ноду. Чтение RDM6300 |
| После прогона **26** | В native-тесте тревога есть в журнале второй стороны, повтор uuid не двоит строку. На живых платах то же самое, когда обе в одном радиоканале | Карты. Эфир этого прогона не гоняли |
| После прогона **27** | Фикстура кадра: пустой список — отказ, карта из списка — OPEN. На плате то же самое, когда модуль на GPIO 38 и образ собран с `-D MESH485_RDM6300=1` | Совместный прогон двух функций. Живой модуль в прогоне 27 не подключали |
| После прогона **28** | Оба сценария на живых платах подряд | — |

Прогон 24 (слушать RS-485 «Орион») к этому стенду не обязателен.

## После 25 — контакт на одной плате

1. Прошить ноду у панели. OLED живой, USB отвечает на `{` как MESH 485.
2. GPIO 47 не замкнут. `EVENT_LIST` без нового `PCN`.
3. Замкнуть контакт на 1 с. Одна запись: `device_id` `PCN-001`, `type` `PCN`, `state` `ALARM`, `source` `GPIO`.
4. Подержать контакт. Второй `ALARM` не появляется.
5. Разомкнуть. Одна запись `state` `NORMAL`.
6. Дребезг короче 50 мс событием не становится.
7. В приложении MeshCore эта строка в чат не приходит. Companion при этом подключается.

Нет оптопары: замкнуть GPIO 47 на GND через кнопку. Это проверка входа, не проверка реле панели.

## После 26 — вторая нода

1. Обе платы в одном радиоканале MeshCore, разные id: `EXT-001` и `EXT-002`.
2. Замыкание на первой даёт `ALARM` на второй (её `EVENT_LIST` или OLED «ТРЕВОГА»).
3. Выключить питание первой и включить снова при замкнутом контакте: на второй одна тревога, не пачка копий.
4. Размыкание даёт `NORMAL` на второй.
5. Выключить радио второй. Первая копит событие локально. После включения радио вторая получает его один раз.
6. Тревога не даёт импульс на GPIO 40.

## После 27 — считыватель

На ноде мониторинга, UART1 не подключён к шине «Орион».

1. Без карт в списке поднести брелок. OLED «ОТКАЗ», GPIO 40 молчит, событие отказа есть.
2. `ACCESS_ADD_CARD` с этой консоли, тот же брелок. Импульс OPEN, зелёная лампа.
3. Убрать питание радиомодуля или дождаться тишины эфира. Повтор шагов 1–2 такой же: список на самой плате.
4. Подержать брелок. В журнал попадает одно чтение, не поток кадров.
5. Мусор в UART увеличивает счётчик ошибок и картой не считается.

## После 28 — вместе

1. Контакт ПЦН замкнут, на мониторе видна тревога, турникет от тревоги не открывается.
2. Карта из списка открывает турникет, пока тревога ещё висит.
3. Выключить ноду у панели. С2000-М на своих индикаторах жива. Монитор помнит последнюю тревогу и по-прежнему читает карты.
4. Flutter на мониторе: в «Событиях» есть `PCN`, в Access — проход.
